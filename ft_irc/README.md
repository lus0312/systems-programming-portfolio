# ft_irc — Linux 논블로킹 TCP 기반 IRC 서버

C++98로 다중 클라이언트 IRC 서버를 구현한 42 네트워크 프로그래밍 과제입니다. 하나의 `poll()` 이벤트 루프에서 여러 연결의 접속 · 수신 · 송신 · 종료를 처리하며, TCP가 메시지 경계를 보장하지 않는 환경에서 명령을 안정적으로 해석하고 전달하는 구조를 설계했습니다.

| 항목 | 내용 |
| --- | --- |
| 인원 | 3인 팀 |
| 언어 · 환경 | C++98, Linux, GNU Make |
| 담당 | 소켓 · 연결 관리, 인증 · 등록, 명령 실행, 채널 관리, 메시지 전달과 연결 종료 |
| 팀원 담당 | 메시지 · 명령어 파싱 |

## 과제 개요

IRC는 서버에 연결한 사용자들이 채널이나 개인 메시지로 대화하는 텍스트 기반 통신 방식입니다. 이 과제의 핵심은 채팅 명령을 처리하는 데서 나아가, TCP로 들어오는 바이트 스트림을 메시지로 해석하고 여러 연결의 상태를 동시에 관리하는 것입니다.

## 설계

| 구성 요소 | 역할 | 연결 |
| --- | --- | --- |
| `Server` | 소켓과 poll 이벤트 관리, 데이터 수신 · 송신 | 클라이언트 소켓 ↔ Controller |
| `Message` | 수신한 명령행을 명령과 인자로 분리 | 명령행 → Controller |
| `Controller` | 인증 · 명령 실행, 응답 생성, 사용자 · 채널 관리 | Message, Client, Channel |
| `Client` | 사용자 정보와 등록 상태, 수신 · 송신 버퍼 보관 | 연결별 데이터 관리 |
| `Channel` | 참여자 · 운영자 · 초대 목록과 채널 모드 관리 | 여러 Client의 채널 참여 상태 |

```text
IRC 클라이언트 → TCP 소켓 → Server / poll
                              │
                         수신 버퍼 누적
                              │
                     명령행 분리 → Message
                                      │
                                  Controller
                                  /        \
                              Client     Channel
                                  │
                              송신 버퍼
                                  │
IRC 클라이언트 ← TCP 소켓 ← Server / POLLOUT
```

## 문제 해결

### 수신이 지연되는 클라이언트가 서버 전체를 막지 않도록

클라이언트가 연결되어 있다고 해서 항상 데이터를 읽고 있는 것은 아닙니다. 수신이 느린 클라이언트가 하나만 있어도 블로킹 방식에서는 서버 전체가 멈출 수 있습니다.

이 상황을 재현하기 위해 같은 채널의 클라이언트 하나를 일시 정지시키고, 다른 클라이언트에서 대량의 메시지를 전송하는 테스트를 구성했습니다. 구현에서는 **메시지를 생성하는 일과 실제 소켓으로 전달하는 일을 분리**해, 전송하지 못한 데이터를 연결별 송신 버퍼에 남기고 소켓이 쓰기 가능해지는 `POLLOUT` 시점에 이어서 보내도록 했습니다. `EAGAIN` · `EWOULDBLOCK`이 발생한 경우에도 같은 경로로 재시도합니다.

테스트 결과 실행 중인 클라이언트는 메시지를 계속 수신했고, 정지했던 클라이언트도 재개 후 밀린 메시지를 받았습니다. 버퍼가 무한히 증가하지 않도록 클라이언트별 송신 버퍼가 32 MiB를 초과하려는 경우 해당 연결을 종료 대상으로 표시합니다.

### 한 번의 수신이 하나의 명령과 일치하지 않는 문제

TCP는 스트림이므로 하나의 명령이 여러 번에 나뉘어 도착하거나, 여러 명령이 한 번에 도착할 수 있습니다. 클라이언트별 수신 버퍼에 데이터를 누적한 뒤 CRLF를 기준으로 완성된 명령행만 분리해 처리하도록 구성했습니다. 수신 단계와 명령 처리 단계를 분리한 뒤로 명령이 간헐적으로 누락되는 현상이 해소됐습니다.

### 자체 서버의 응답만으로는 구현을 판단하기 어려운 문제

직접 만든 서버가 예상한 응답을 돌려준다는 사실만으로는 프로토콜을 올바르게 구현했는지 확인하기 어려웠습니다. Libera.Chat에 접속해 실제 서버의 응답 코드와 상태 변화를 관찰하고 이를 비교 기준으로 삼았습니다. 검증에는 `irssi`, `nc`, 통신 trace를 기록하는 테스트 스크립트를 사용해 정상적인 대화뿐 아니라 메시지 분할 전송, 다중 접속, 비정상 종료 상황까지 확인했습니다.

## 주요 구현

- Linux 소켓에 `O_NONBLOCK`을 적용하고 `poll()`로 여러 연결의 읽기 · 쓰기 준비 상태 감시
- `PASS`, `NICK`, `USER`를 통한 인증 · 등록과 닉네임 중복 확인
- `JOIN`, `PART`, `QUIT` 및 사용자 · 채널 대상 `PRIVMSG` 처리
- `TOPIC`, `KICK`, `INVITE`와 채널 모드 `i`, `t`, `k`, `o`, `l` 구현
- 클라이언트별 수신 데이터 누적 후 CRLF 기준 명령행 분리
- 부분 송신 시 미전송 데이터를 송신 버퍼에 유지하고 다음 `POLLOUT`에서 재시도
- 채널 이름의 대소문자 비교 통일, 연결 종료 시 공통 채널 사용자에게 알림
- 송신 메시지를 CRLF 포함 512바이트에 맞추고, 긴 NAMES 목록은 여러 응답으로 분리
- 닉네임 최대 30자 제한

## 배운 점

**TCP 데이터와 메시지 경계** — 한 번의 수신이 명령 하나와 일치한다고 가정할 수 없습니다. 데이터를 모으는 단계와 완성된 명령을 처리하는 단계를 구분해야 했습니다.

**연결별 상태와 공유 상태** — 인증 정보와 수신 · 송신 버퍼는 사용자별로, 채널의 참여자 · 운영자 · 모드는 여러 사용자가 공유하는 상태로 관리했습니다. 명령 처리 결과가 응답 메시지뿐 아니라 이후 접근 권한과 연결 정리에까지 영향을 준다는 점을 다뤘습니다.

**정상 동작 밖의 상황을 검증하는 방법** — 클라이언트의 수신을 멈추거나 명령을 나눠 보내는 방식으로, 평범한 대화만으로는 만들 수 없는 조건을 재현했습니다. 기능의 성공 여부뿐 아니라 상태 변화와 오류 응답까지 확인하는 방향으로 테스트를 넓혔습니다.

## 실행 방법

Linux 환경과 C++ 컴파일러, GNU Make가 필요합니다. 아래 명령은 `ft_irc` 폴더 안에서 실행합니다.

```bash
make
./ircserv 6667 local-test-password
```

다른 터미널에서 `irssi`로 접속한 뒤 `/join #portfolio`로 채널에 입장합니다. 두 번째 클라이언트는 다른 닉네임을 사용합니다.

```bash
irssi -c 127.0.0.1 -p 6667 -w local-test-password -n alice
```

Python 3가 설치되어 있으면 테스터로 서버를 실행하고 통신 trace를 확인할 수 있습니다.

```bash
python3 ft_irc_tester_trace.py --spawn ./ircserv --port 6667 --password local-test-password --trace
```

`test_partial.sh`는 포트 `6667`, 비밀번호 `secret`을 사용하므로 실행할 서버의 설정과 맞춰야 합니다.

빌드 결과물은 `objs/`에 저장됩니다. `make clean`은 빌드 결과물을, `make fclean`은 실행 파일까지 제거합니다.
