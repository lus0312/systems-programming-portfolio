# pipex — 셸의 파이프를 직접 구현한 프로세스 간 통신

셸의 `< file1 cmd1 | cmd2 > file2`를 C로 재현한 42 시스템 프로그래밍 과제입니다. 두 명령을 각각 프로세스로 실행하고, 앞 명령의 출력을 뒤 명령의 입력으로 연결하는 파이프의 동작 원리를 다뤘습니다.

| 항목 | 내용 |
| --- | --- |
| 인원 | 개인 과제 |
| 언어 · 환경 | C, Linux, GNU Make, Valgrind |
| 담당 | 전 범위 (인자 · 파일 처리, 명령 분리와 경로 탐색, fork · pipe · dup2 · execve, 종료 상태 전달, 자원 정리) |

## 과제 개요

```bash
./pipex infile "grep a1" "wc -w" outfile      # < infile grep a1 | wc -w > outfile 과 같은 결과
```

인자는 입력 파일, 명령 두 개, 출력 파일입니다. 명령은 셸이 아니라 프로그램(`execve`)이 직접 실행하므로 명령 문자열을 나누고, 실행 파일을 찾고, 입출력을 연결하는 일을 전부 직접 처리해야 합니다. 셸 없이 `|`가 무엇을 하는지 구현으로 확인하는 과제입니다.

## 설계

| --- | --- | --- |
| 메인 흐름 | 인자 검사, 파일 열기, 파이프 생성, 자식 두 개 생성, 종료 상태 회수 | `pipex.c` |
| 명령 분리 | 따옴표를 처리하며 명령 문자열을 인자 배열로 분리 | `pipex_utils_5.c` |
| 경로 탐색 | 경로가 포함된 명령 검사, `PATH` 탐색, 실행 권한 확인 | `pipex_utils_3.c` |
| 실행 | `dup2`로 입출력 연결, 안 쓰는 fd 닫기, `execve` | `pipex_utils_3.c` |
| 오류 처리 · 정리 | 셸 형식 오류 메시지, 종료 코드, 자원 해제 | `pipex_utils_2.c`, `pipex_utils_4.c` |
| 문자열 유틸 | 허용 함수 제한 때문에 직접 구현한 문자열 함수 | `pipex_utils_1.c`, `ft_split.c` |

```text
 infile ──→ [ cmd1 ] ──→ ( pipe: 커널 버퍼 ) ──→ [ cmd2 ] ──→ outfile
            자식 1        fd[1]에 쓰면 fd[0]으로     자식 2
            stdin: infile   읽힘                    stdout: outfile
            stdout: fd[1]                           stdin: fd[0]

 부모: 파이프 양 끝을 닫고 → 자식 둘을 waitpid → cmd2의 종료 상태를 자신의 종료 코드로 반환
```

## 문제 해결

### `|`가 무엇인지 이해하기

셸에서 `|`는 한 글자지만, 구현하려면 안에서 일어나는 일을 풀어서 이해해야 했습니다.

- `pipe(fd)`는 **커널 안의 버퍼**를 만들고 그 양 끝을 가리키는 fd 두 개를 돌려줍니다(`fd[1]`에 쓰면 `fd[0]`으로 읽힘).
- 명령은 자신이 어디에 연결되어 있는지 모르고, 그냥 표준 입력(0)에서 읽고 표준 출력(1)에 씁니다. 그래서 자식에서 `dup2`로 fd 0 또는 1을 파이프나 파일로 **바꿔치기**한 뒤 `execve`하면, 명령은 바뀐 입출력을 그대로 사용합니다.
- `fork`는 fd 테이블도 복사합니다. 부모와 두 자식이 파이프의 양 끝을 모두 들고 있으므로, **각자 쓰지 않는 끝을 닫아야** 합니다. 읽는 쪽은 "쓰는 끝이 모두 닫혔을 때"에야 EOF를 받기 때문입니다.

마지막 항목은 실제로 확인할 수 있습니다. 부모나 자식 중 한 곳이라도 쓰기 끝을 닫지 않으면, 뒤 명령(`wc`)이 EOF를 못 받고 끝나지 않습니다. 이 프로그램에서는 부모가 파이프 양 끝을 닫고, 자식 1은 읽는 끝을, 자식 2는 쓰는 끝을 닫도록 구성했습니다. 입출력 연결이 끝난 뒤에는 원래 파일 fd(`infile`, `outfile`)도 닫아 자식이 불필요한 fd를 들고 실행되지 않게 했습니다.

### 어디까지 구현할 것인가

셸의 `|`는 사용 방식이 매우 다양해서 범위를 정하기 어려웠습니다. 과제에는 "확신이 없으면 `< file1 cmd1 | cmd2 > file2`를 실행했을 때의 셸 동작과 같게 처리"하라는 기준이 있어, **셸의 동작을 판단 기준**으로 삼았습니다. 의심이 드는 경우마다 같은 명령을 셸로 직접 실행해 결과를 비교하고 그대로 따랐습니다.

| 상황 | 동작 (bash와 동일) |
| --- | --- |
| 입력 파일이 없거나 열 수 없음 | 오류 메시지를 출력하지만 **두 번째 명령은 계속 실행** (입력은 빈 상태) |
| 명령을 찾을 수 없음 | `pipex: cmd: command not found`, 종료 코드 127 |
| 경로가 포함된 명령 (`/bin/cat`) | `PATH`를 뒤지지 않고 그 경로를 직접 검사 (없으면 127, 실행 권한 없으면 126) |
| 실행 권한이 없거나 디렉터리 | `Permission denied`, 종료 코드 126 |
| 따옴표가 든 인자 (`awk '{print $1}'`, `grep "a b"`) | 따옴표 안의 공백은 분리하지 않고, 따옴표는 제거 |
| 빈 명령 (`""`) | `command not found`, 종료 코드 127 |
| `PATH`가 없는 환경 | 경로 지정 명령만 실행 가능 |
| 전체 종료 코드 | **마지막 명령의 상태** (시그널로 죽었다면 128 + 시그널 번호) |

범위에서 제외한 것도 분명히 했습니다.
- **보너스**(여러 파이프 `cmd1 | cmd2 | ... | cmdn`, `here_doc`)는 구현하지 않았습니다.
- 명령은 `execve`로 직접 실행하므로 **셸 문법**(`$HOME` 확장, `*`, `&&`, 백슬래시 이스케이프)은 지원하지 않습니다. 명령 문자열은 공백과 따옴표로만 나눕니다.

### 확인 방법

같은 입력을 pipex와 셸의 `< file1 cmd1 | cmd2 > file2`에 각각 넣고, 출력 파일 내용과 종료 코드를 나란히 비교했습니다. 정상 입력(`ls -l`, `grep`, `wc`), 절대경로, 따옴표 인자, 없는 명령, 빈 명령, 없는 입력 파일, 디렉터리 실행, 실행 후 실패(`false`), 일정 시간 실행되는 명령(`sleep`)을 확인했습니다. Valgrind로 누수와 잘못된 접근도 점검했고, 자식 프로세스까지 추적하도록 `--trace-children=yes`를 사용했습니다.

## 주요 구현

- `open` / `pipe` / `fork` / `dup2` / `execve` / `waitpid`를 조합한 두 프로세스 파이프라인
- 따옴표를 처리하는 명령 분리기 직접 구현, 허용 함수 제한에 맞춘 문자열 함수(`ft_strchr_p`, `ft_strdup_p` 등) 구현
- 경로 지정 명령 / `PATH` 탐색 분리, 실행 권한(`X_OK`) 확인
- 셸 형식의 오류 메시지와 종료 코드(127, 126, 마지막 명령 상태, 시그널 종료)
- 입력 파일이 없을 때도 다음 명령이 실행되도록 자식별로 오류 처리
- 사용하지 않는 fd 닫기와 오류 경로를 포함한 메모리 · fd 정리

## 배운 점

**파이프는 fd 두 개를 이어 주는 커널 버퍼입니다** — 명령은 입출력의 연결 대상을 몰라도 되고, `dup2`로 fd 0과 1을 바꾸면 됩니다. 셸이 가진 리다이렉션과 파이프의 원리를 프로세스와 fd 관점에서 설명할 수 있게 됐습니다.

**fd는 프로세스 사이에서 복사됩니다** — `fork` 이후 누가 어느 fd를 닫아야 하는지가 프로그램의 종료 여부를 좌우했습니다. 열려 있는 쓰기 끝 하나 때문에 읽는 쪽이 끝나지 않는 상황을 겪었습니다.

**요구사항이 모호하면 기준을 정하고 그 기준으로 검증합니다** — 사용 방식이 많은 기능은 모든 경우를 만들기보다 기준(실제 셸의 동작)을 정하고, 그 기준과 나란히 비교하며 범위를 확정했습니다.

## 실행 방법

Linux 환경과 C 컴파일러, GNU Make가 필요합니다. 아래 명령은 `pipex` 폴더 안에서 실행합니다.

```bash
make
printf "hello a1\nworld\nfoo a1 bar\n" > infile
./pipex infile "grep a1" "wc -w" outfile
cat outfile
```

셸의 결과와 비교하려면 다음처럼 실행해 볼 수 있습니다.

```bash
< infile grep a1 | wc -w                    # 셸에서 직접 실행한 결과
./pipex infile "/bin/cat" "wc -l" outfile   # 경로가 포함된 명령
./pipex infile "nocmd" "wc -l" outfile      # command not found (127)
echo $?
```

```bash
valgrind --leak-check=full --trace-children=yes ./pipex infile "grep a1" "wc -w" outfile
```

`make clean`은 오브젝트 파일을, `make fclean`은 실행 파일까지 제거합니다.
