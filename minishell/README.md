# minishell — 프로세스 · 파이프 · 시그널을 다루는 Linux 셸

C로 bash를 축소 구현한 42 시스템 프로그래밍 과제입니다. 입력한 명령을 프로세스로 실행하고, 파이프와 리다이렉션으로 연결하며, Ctrl-C · Ctrl-D 같은 중단 상황을 셸이 죽지 않게 처리하는 구조를 다뤘습니다.

| 항목 | 내용 |
| --- | --- |
| 인원 | 2인 팀 |
| 언어 · 환경 | C, Linux, GNU Make, GNU readline, Valgrind |
| 담당 | 실행부 전체 (프로세스 생성과 회수, 파이프, 리다이렉션 fd 처리, 외부 명령 실행, 빌트인, 시그널 · 터미널, heredoc, 종료 상태) |
| 팀원 담당 | 입력 검사 · 토큰 분리 · 변수 확장 |

## 과제 개요

셸은 입력을 읽어 해석하고, 프로세스를 만들어 실행하고, 결과를 기다리는 일을 반복하는 프로그램입니다. 이 과제의 핵심은 문자열 처리보다 **프로세스와 파일 디스크립터를 정확히 다루는 것**입니다. `fork`, `execve`, `pipe`, `dup2`, `waitpid`를 조합해 `ls | grep a > out`처럼 여러 명령이 연결된 입력을 bash와 같은 결과로 실행해야 합니다.

지원 기능은 다음과 같습니다.

- 프롬프트와 명령 히스토리(`readline`)
- `PATH` 탐색, 상대 · 절대 경로 실행
- 따옴표 처리, 환경 변수 `$VAR`, 종료 상태 `$?`
- 리다이렉션 `<` `>` `>>` `<<`(heredoc), 파이프 `|`
- `Ctrl-C`, `Ctrl-D`, `Ctrl-\` 동작
- 빌트인 `echo -n`, `cd`, `pwd`, `export`, `unset`, `env`, `exit`

## 설계

| 구성 요소 | 역할 | 연결 |
| --- | --- | --- |
| 메인 루프 (`main.c`) | 입력 읽기, 히스토리, 환경 변수 리스트 관리, 종료 상태 보관 | readline ↔ 실행부 |
| 입력 파서 | 입력 검사, 명령 단위 분리, 토큰 분리와 변수 확장 | 명령 리스트 → 실행부 |
| 단일 명령 실행 (`run_minishell.c`) | 빌트인은 셸 안에서 실행하고, 외부 명령은 fork 후 실행 | 파서 결과, 종료 상태 |
| 파이프 실행 (`run_pipe_*.c`) | 파이프 개수만큼 fd 배열과 자식 생성, 입출력 연결, 전체 회수 | 여러 자식 프로세스 |
| 외부 명령 (`ft_excute_*.c`) | `PATH` 탐색, 실행 가능 검사, 환경 배열 생성, `execve` | 환경 변수 리스트 |
| 리다이렉션 fd (`handle_fd.c`) | 열어 둔 fd를 stdin/stdout에 연결하고 남은 fd 정리 | 명령 노드 |
| 시그널 · 터미널 (`handle_signal.c`, `handle_terminal.c`) | 상황별 Ctrl-C 처리, 터미널 설정 | 전역 상태 변수 |
| 빌트인 (`builtin_*.c`) | 셸 상태를 바꾸는 명령 구현 | 환경 변수 리스트 |

```text
readline ──→ 입력 검사 / 파싱 ──→ 명령 리스트 (CMD / PCMD)
                                       │
                 ┌─────────────────────┴───────────────────────┐
             단일 명령 (CMD)                              파이프 묶음 (PCMD)
                 │                                              │
        빌트인? ── 예 → 셸 프로세스에서 실행             pipe() × N, fork() × (N+1)
             └ 아니오 → fork                              각 자식: dup2로 입출력 연결
                          │                                         │
                    자식: 리다이렉션 dup2               빌트인이면 실행 후 exit,
                          → PATH 탐색 → execve          아니면 execve
                          │                                         │
                    부모: waitpid  ←──────────────── 부모: 모든 자식 waitpid
                          │
                    종료 상태 → $?
```

환경 변수는 `envp`를 연결 리스트로 복사해 관리합니다. 각 항목에 내보내진 변수(`ENV`)인지 해제된 변수(`UNSET`)인지 표시가 붙고, 외부 명령을 실행할 때 이 리스트를 `execve`용 배열로 다시 만듭니다.

## 문제 해결

### 같은 Ctrl-C가 상황마다 다른 일을 해야 하는 문제

Ctrl-C는 프롬프트에서 대기 중일 때, 명령이 실행 중일 때, heredoc 입력 중일 때 각각 해야 할 일이 다릅니다. 게다가 터미널은 시그널을 셸과 자식 프로세스에 동시에 보냅니다. 핸들러 안에서는 메인 자료구조에 접근하지 않고 시그널 번호만 전역 변수에 저장해야 하는 과제 규칙도 지켜야 했습니다.

전역 변수 하나(`volatile sig_atomic_t`)를 **현재 상황을 나타내는 상태 값**으로 사용했습니다.

| 값 | 의미 | 핸들러 동작과 이후 처리 |
| --- | --- | --- |
| `0` | 프롬프트 대기 | 줄바꿈 후 `readline`의 입력 버퍼를 비우고(`rl_replace_line`) 새 프롬프트를 표시, `130`으로 변경 |
| `1` | 자식이 실행 중 | 줄바꿈만 출력하고 `-1`로 표시, 프롬프트는 다시 그리지 않고 `waitpid`로 회수 |
| `-1` | 실행 중 중단됨 | heredoc이라면 명령 전체를 취소, 아니면 종료 상태를 130으로 처리 |
| `130` | 프롬프트에서 중단 | 다음 명령의 `$?`가 130이 되도록 종료 상태에 반영 |

자식 프로세스는 `fork` 직후 `SIGINT` · `SIGQUIT`를 기본 동작으로 되돌립니다. 그렇게 하지 않으면 프롬프트용 핸들러를 물려받아 Ctrl-C로 자식이 종료되지 않았습니다. 프롬프트에서 Ctrl-C를 누르면 종료 상태를 낼 프로세스가 없으므로, 전역 상태 값에서 `$?`를 직접 만들어 냅니다. 시그널로 종료된 자식은 `WIFSIGNALED` / `WTERMSIG`로 `128 + 시그널 번호`를 계산합니다.

Ctrl-D는 시그널이 아니라 터미널이 보내는 EOF입니다. 빈 줄에서는 `readline`이 `NULL`을 반환해 셸을 정리하고 종료하고, 글자가 있는 줄에서는 무시되며, heredoc 입력 중에는 입력 종료로 처리합니다.

### heredoc 입력 중 Ctrl-C 처리

`<<`는 구분자 줄이 나올 때까지 입력을 받아 명령의 입력으로 넘겨야 합니다. 입력 도중 Ctrl-C가 오면 heredoc뿐 아니라 그 명령 전체가 취소되어야 하고, 셸은 살아 있어야 합니다.

입력을 받는 일을 **별도 자식 프로세스**로 분리했습니다. 자식은 시그널 기본 동작을 사용해 Ctrl-C가 오면 즉시 종료되고, 입력 내용은 파이프로 부모에 전달합니다. 부모는 자식이 끝난 뒤 전역 상태 값이 `-1`(중단됨)이면 파이프를 닫고 명령을 취소하며 종료 상태를 130으로 설정합니다. 정상 종료라면 파이프의 읽는 끝을 명령의 입력으로 연결합니다.

```text
부모: pipe() → fork ─┬─ 자식: 쓰는 끝을 stdout에 연결 → 한 줄씩 읽기 → 구분자면 종료, 아니면 파이프에 기록
                    └─ 부모: waitpid → 중단됐으면 명령 취소(130), 아니면 읽는 끝을 stdin으로 사용
```

구분자에 따옴표가 없으면 입력한 줄의 `$VAR`를 확장하고, 따옴표가 있으면 그대로 기록합니다. 입력을 1바이트씩 읽어 한 줄을 조립하므로 표준 입력을 필요 이상으로 소비하지 않습니다.

### 검증 방법

기능마다 bash와 같은 입력을 넣어 출력과 종료 상태를 나란히 비교하고, Valgrind로 누수와 잘못된 접근을 함께 확인했습니다. 시그널은 실제 터미널 환경(pty)에서 Ctrl-C, Ctrl-D, Ctrl-\를 프롬프트, 명령 실행 중, 파이프 중, heredoc 중으로 나누어 조합하고 종료 상태까지 비교했습니다.

## 주요 구현

- `fork` / `execve` / `waitpid`로 외부 명령 실행, `PATH` 탐색과 경로 지정 실행
- 명령 없음(127), 실행 불가 · 디렉터리(126) 종료 코드와 메시지
- `pipe` / `dup2`로 N개 명령 연결, 안 쓰는 fd 닫기, 프로세스별 자원 해제
- 빌트인은 셸 프로세스에서 실행하고, 출력 리다이렉션이 있으면 출력 시에만 자식을 만들어 처리
- 리다이렉션 `<` `>` `>>` `<<`의 fd를 명령 실행 직전에 연결하고 나머지 fd 정리
- 환경 변수 리스트(`ENV` / `UNSET`)와 `export`, `unset`, `env`, `cd`의 `PWD` · `OLDPWD` 갱신
- 종료 상태 계산: 정상 종료, 시그널 종료(128 + n), 파이프는 마지막 명령 기준
- `execve` 실패나 오류 경로에서도 부모로부터 복제된 메모리를 정리하고 종료

## 배운 점

**시그널은 상황에 따라 의미가 달라집니다** — 같은 Ctrl-C라도 대기 중인 셸, 실행 중인 자식, 입력 중인 heredoc이 각각 다르게 반응해야 했습니다. 핸들러가 할 수 있는 일이 제한적이라서, 상태를 하나의 값으로 표현하고 부모가 그 값을 읽어 다음 동작을 결정하는 방식이 필요했습니다.

**프로세스마다 fd와 메모리의 소유가 갈립니다** — `fork` 이후 자식은 부모의 fd와 메모리 복사본을 그대로 가집니다. 어떤 프로세스가 어느 fd를 닫아야 하는지, `execve` 전에 무엇을 정리해야 하는지를 정하지 않으면 파이프가 닫히지 않아 멈추거나 누수가 생깁니다.


## 실행 방법

Linux 환경과 C 컴파일러, GNU Make, `readline` 개발 라이브러리(`libreadline-dev`)가 필요합니다. 아래 명령은 `minishell` 폴더 안에서 실행합니다.

```bash
make
./minishell
```

실행 후 다음처럼 확인할 수 있습니다.

```bash
minishell: echo "hello $USER" | cat -e
minishell: cat << EOF | wc -l
minishell: ls -l > out.txt
minishell: cat out.txt
minishell: false | true
minishell: echo $?
```

메모리 사용은 Valgrind로 확인할 수 있습니다.

```bash
valgrind --leak-check=full --show-leak-kinds=all ./minishell
```

빌드 결과물은 `src/*.o`이며, `make clean`은 오브젝트를, `make fclean`은 실행 파일까지 제거합니다.
